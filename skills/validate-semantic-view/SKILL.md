# Validate Semantic View

## Overview

Produces an evidence-backed validation report for a **deployed** Semantic View (SV), checked against reference data and a baseline definition. Use this skill to validate deployed semantic views against reference data and a baseline. Pre-deployment YAML syntax validation is outside its scope. Each check ends in exactly one status:

| Status | Meaning |
|---|---|
| **PASS** | Check ran and the evidence meets the criterion |
| **FAIL** | Check ran and the evidence violates the criterion |
| **SKIP** | Check could not run. Always state why (missing input, privilege, no active warehouse, unsupported construct, unclassified SQL) |

Every status carries evidence: the SQL that ran, the values it returned, and the diff it produced. A status without evidence is not allowed.

### Relationship to `semantic-view-patterns`

| Area | `semantic-view-patterns` | This skill |
|---|---|---|
| Purpose | Teach and apply modeling patterns, then deploy | Audit an SV that already exists, without changing it |
| Fanout / wrong PK | `sv_diagnostics` 5b explains the trap and gives one ungrouped `SUM` detection query | Counts right-side matches per left row on every relationship and estimates metric impact |
| Raw SQL comparison | Ad-hoc tip | Formal reconciliation: same grain, same filters, null-safe row-level diff, tolerance, verdict |
| Introspection | `introspection` lists `DESCRIBE`/`SHOW` commands | Uses those commands as inputs to checks |
| Version diff | Not covered | Structured baseline diff: formulas, relationships, removed fields |
| Writes objects | Yes (tutorial deploy, apply mode) | Never |

When a check fails, point the user to the relevant `semantic-view-patterns` snippet for the fix (for example `sv_diagnostics`, `multi_path_metrics`, or `semi_additive_metric`). Do not apply the fix from this skill.

## Read-Only Guardrails

Every statement, whether supplied by the user or generated by this skill, must pass both lists below. **If any statement or function cannot be confidently classified, do not execute it.** Mark the affected check **SKIP** with the unclassified item as the reason.

**Approved statements** (nothing else):

| Statement | Scope |
|---|---|
| `SELECT ...` / `WITH ... SELECT ...` | A single statement with no `;`-separated statements after it |
| `DESCRIBE SEMANTIC VIEW <fqn>` | |
| `SHOW SEMANTIC VIEWS`, `SHOW SEMANTIC DIMENSIONS`, `SHOW SEMANTIC METRICS`, `SHOW SEMANTIC FACTS` | Optional `IN`/`LIKE`/`FOR METRIC` clauses |

**Approved functions** (finite list; any other function name is rejected):

| Category | Functions |
|---|---|
| Semantic view | `SEMANTIC_VIEW`, `SYSTEM$READ_YAML_FROM_SEMANTIC_VIEW` |
| Session | `CURRENT_WAREHOUSE` |
| Aggregate | `SUM`, `COUNT` (including `COUNT(DISTINCT ...)`), `COUNT_IF`, `MIN`, `MAX`, `AVG` |
| Window | `ROW_NUMBER`, plus the aggregates above used with `OVER (...)` |
| Null handling and logic | `COALESCE`, `NULLIF`, `IFF`, `EQUAL_NULL` |
| Numeric | `ABS`, `ROUND` |
| Type conversion | `CAST` / `::`, `TRY_CAST`, `TO_DATE`, `TO_NUMBER` |
| Date | `DATE_TRUNC`, `DATE_PART`, `EXTRACT`, `YEAR`, `QUARTER`, `MONTH`, `DAY`, `DATEADD` |
| String | `UPPER`, `LOWER`, `TRIM` |

`CASE`, arithmetic, comparison operators, `IN`, `BETWEEN`, `LIKE`, `IS [NOT] NULL`, and the logical operators are expressions, not function calls, and are allowed.

The following are always rejected, even if a name looks similar to an approved one: database- or schema-qualified calls (UDFs, `SNOWFLAKE.CORTEX.*`), other table functions, other `SYSTEM$*` functions (including `SYSTEM$CREATE_SEMANTIC_VIEW_FROM_YAML` in dry-run mode), `AI_*` functions, external functions, `<seq>.NEXTVAL`, `RESULT_SCAN`, `CALL`, `EXECUTE IMMEDIATE`, DDL, DML, `GRANT`, and temp tables.

**Before running user-supplied reference SQL:**
1. Confirm it is a single approved statement.
2. List every function call it contains and match each one against the approved list. Show the list to the user.
3. If anything is rejected or unclassified, do not run it. Mark Check 1 **SKIP** and name the item. The user may supply a rewrite.

Add a `LIMIT` to row-level evidence shown to the user. Counts and totals are always computed over the full result before any evidence is limited.

## Inputs

Collect these up front and skip anything the user already supplied. A missing input SKIPs its check and does not block the other checks.

| Input | Needed by | Source |
|---|---|---|
| SV fully qualified name | All | User. Use `snowflake_object_search` only if the user gives a vague name |
| Metric(s) and grain dimension(s) | Check 1, 2 | User |
| Filter(s) | Check 1, 2 | User, or none |
| Reference SQL | Check 1 | User-pasted query or a file path |
| Tolerance | Check 1 | Default: exact for counts, `ABS(diff) <= 0.01` for decimals. Ask before loosening it |
| Baseline definition | Check 3 | YAML or DDL file, pasted text, or a second SV FQN (for example `SALES_SV_V1`) |
| Active warehouse | Check 1, 2 | The session's current warehouse, or an existing warehouse the user selects (Step 0a). Not needed for Check 3 |

## Workflow

### Step 0: Load the current definition

```sql
SELECT SYSTEM$READ_YAML_FROM_SEMANTIC_VIEW('<DB>.<SCHEMA>.<SV>');
DESCRIBE SEMANTIC VIEW <DB>.<SCHEMA>.<SV>;
```

Parse out:
- Tables, with base table and primary key
- Relationships: left table and columns → right table and columns, and the join type
- Facts and dimensions
- Metrics: name, table, expression, `USING`, `NON ADDITIVE BY`, and whether the metric is **additive**. Only a plain `SUM` of row-level facts counts as additive. Ratios, `COUNT(DISTINCT)`, `AVG`, `MIN`/`MAX`, derived metrics, and `NON ADDITIVE BY` metrics are non-additive.

If both commands fail, mark every check SKIP with the error text and stop.

### Step 0a: Confirm an active warehouse for Checks 1 and 2

Checks 1 and 2 query table data and the SV, so they need an active warehouse in the SQL session that runs them. Step 0 and Check 3 only read definitions; do not block them on this step.

1. Run `SELECT CURRENT_WAREHOUSE();`. If it returns a name, record it for the inventory and continue.
2. If it returns NULL, ask the user to select an existing warehouse for the same SQL session that will run Checks 1 and 2. This skill does not list, set, create, or alter warehouses.
3. After the user responds, run `SELECT CURRENT_WAREHOUSE();` again in that session. If it still returns NULL, mark Checks 1 and 2 **SKIP** ("no active warehouse in the SQL session") and continue with Check 3 when both definitions are available.
4. If a Check 1 or Check 2 query later reports that no warehouse is active, apply steps 2–3 again. Do not retry the query until the recheck returns a warehouse.

**⚠️ STOP**: Show the parsed inventory (counts plus the metrics in scope and their additivity), the warehouse for Checks 1 and 2 (or that none is available), and the planned checks. Proceed after the user confirms.

### Check 1: Metric Reconciliation

**Criterion**: Both sides return the same set of grain keys, each key appears once per side, and for every key the SV metric equals the reference value within tolerance. NULL and zero are different values.

1. **Align the grain and filters before running anything.** Write a side-by-side alignment table:

   | Aspect | SV query | Reference SQL |
   |---|---|---|
   | Grain | `DIMENSIONS sales_date.month` | `DATE_TRUNC('month', order_date)` |
   | Grain type | `DATE` | cast to `DATE` |
   | Filter | `WHERE sales_date.year = 2025` | `WHERE YEAR(order_date) = 2025` |
   | Measure | `METRICS order_lines.total_revenue` | `SUM(quantity * unit_price)` |

   Cast grain columns to the same type on both sides (for example `DATE` vs `TIMESTAMP_NTZ`). Otherwise equal values will not join. If the grain or filters cannot be matched, mark the check **SKIP** and name the mismatch. A mismatched comparison must never yield PASS or FAIL.

2. **Probe both inputs for duplicate grain keys** before comparing. `GROUP BY` treats NULL as one group, so nullable keys are covered:

   ```sql
   WITH sv  AS (SELECT * FROM SEMANTIC_VIEW(<SV> DIMENSIONS <dims> METRICS <metric> WHERE <filters>)),
        ref AS (<reference SQL>)
   SELECT 'SV' AS input, <k1>, <k2>, COUNT(*) AS rows_per_key FROM sv GROUP BY ALL HAVING COUNT(*) > 1
   UNION ALL
   SELECT 'REFERENCE', <k1>, <k2>, COUNT(*) FROM ref GROUP BY ALL HAVING COUNT(*) > 1
   ORDER BY rows_per_key DESC
   LIMIT 50;
   ```

   If any row is returned, mark the check **SKIP**. Report which input has duplicates (`SV`, `REFERENCE`, or both) and show the duplicated keys. Do not compare.

3. **Compare in one statement**, using presence flags and null-safe joins on every grain column. The outcome counts and the evidence sample come from the same `cmp` result, so they always describe the same data. Window aggregates are computed over all rows before `QUALIFY` limits the sample:

   ```sql
   WITH sv  AS (SELECT <k1>, <k2>, <metric> AS v, TRUE AS present
                FROM SEMANTIC_VIEW(<SV> DIMENSIONS <dims> METRICS <metric> WHERE <filters>)),
        ref AS (SELECT <k1>, <k2>, <metric> AS v, TRUE AS present FROM (<reference SQL>)),
        cmp AS (
          SELECT IFF(sv.present, sv.<k1>, ref.<k1>) AS <k1>,
                 IFF(sv.present, sv.<k2>, ref.<k2>) AS <k2>,
                 sv.v AS sv_value,
                 ref.v AS ref_value,
                 CASE
                   WHEN sv.present IS NULL              THEN 'MISSING_IN_SV'
                   WHEN ref.present IS NULL             THEN 'MISSING_IN_REF'
                   WHEN sv.v IS NULL AND ref.v IS NULL  THEN 'MATCH'
                   WHEN sv.v IS NULL OR ref.v IS NULL   THEN 'NULL_MISMATCH'
                   WHEN ABS(sv.v - ref.v) > <tolerance> THEN 'VALUE_MISMATCH'
                   ELSE 'MATCH'
                 END AS outcome
          FROM sv FULL OUTER JOIN ref
            ON EQUAL_NULL(sv.<k1>, ref.<k1>) AND EQUAL_NULL(sv.<k2>, ref.<k2>)
        )
   SELECT cmp.*,
          COUNT(*)                           OVER () AS total_keys,
          COUNT_IF(outcome = 'MATCH')          OVER () AS n_match,
          COUNT_IF(outcome = 'MISSING_IN_SV')  OVER () AS n_missing_in_sv,
          COUNT_IF(outcome = 'MISSING_IN_REF') OVER () AS n_missing_in_ref,
          COUNT_IF(outcome = 'NULL_MISMATCH')  OVER () AS n_null_mismatch,
          COUNT_IF(outcome = 'VALUE_MISMATCH') OVER () AS n_value_mismatch,
          -- Additive metrics only; omit these two lines otherwise:
          SUM(sv_value)                      OVER () AS sv_total,
          SUM(ref_value)                     OVER () AS ref_total
   FROM cmp
   QUALIFY ROW_NUMBER() OVER (
             ORDER BY IFF(outcome = 'MATCH', 1, 0), outcome,
                      ABS(sv_value - ref_value) DESC NULLS FIRST) <= 50
   ORDER BY IFF(outcome = 'MATCH', 1, 0), outcome, ABS(sv_value - ref_value) DESC NULLS FIRST;
   ```

   Read the counts from any returned row; they are identical on every row. The sample lists mismatches first and shows `MATCH` rows only when fewer than 50 mismatches exist.

   **Totals for non-additive metrics** (ratios, distinct counts, averages, `NON ADDITIVE BY`): omit `sv_total`/`ref_total`, because summing per-key values is meaningless. If a total is wanted, compare at the total grain instead: query the SV with no `DIMENSIONS` and the reference with no `GROUP BY` under the same filters, then label the result "total-grain comparison".

4. **Verdict**:
   - Statement returns zero rows: **SKIP** ("no rows under the supplied filters on either side").
   - `n_match = total_keys`: **PASS**.
   - Anything else: **FAIL**. Report every `n_*` count, the totals if the metric is additive, and the evidence sample.

### Check 2: Relationship Fanout

**Criterion**: For a nonempty left population, no left row matches more than one right row. Unmatched left rows are reported as a separate finding and do not change the status.

1. **Prerequisites** for each equality relationship `L(fk) REFERENCES R(pk)`:
   - `L` must have a declared primary key that is unique in its data. Check it with `COUNT(*) = COUNT(DISTINCT <L_pk>)`. If there is no key or it is not unique, mark **SKIP** ("left rows cannot be identified").
   - Range and ASOF relationships: **SKIP** ("match count depends on the window, not a key").
   - Apply the Check 1 filters to `L`. If a filter cannot be expressed on `L`'s base table (for example, it references a dimension on another table), run the counts on unfiltered `L` and state that in the evidence.

2. **Count right-side matches per left row.** Use `=`, not `EQUAL_NULL`, to mirror the equality join, so a NULL FK counts as unmatched:

   ```sql
   WITH l AS (SELECT * FROM <L_base> WHERE <filters on L>),
        r AS (SELECT <pk_cols>, 1 AS hit FROM <R_base>),
        per_row AS (
          SELECT l.<L_pk>, COUNT(r.hit) AS match_cnt
          FROM l LEFT JOIN r ON l.<fk1> = r.<pk1> AND l.<fk2> = r.<pk2>
          GROUP BY l.<L_pk>
        )
   SELECT COUNT(*)                AS left_rows,
          COUNT_IF(match_cnt = 0) AS unmatched_rows,
          COUNT_IF(match_cnt = 1) AS single_matched_rows,
          COUNT_IF(match_cnt > 1) AS multi_matched_rows,
          SUM(match_cnt)          AS joined_rows,
          MAX(match_cnt)          AS max_matches_per_row
   FROM per_row;
   ```

   Report unmatched rows and multiply matched rows **separately**. In a raw `joined_rows / left_rows` ratio they can cancel each other out.

3. **Estimated impact (calculated, not observed).** Compute this only when all of these hold:
   - The metric is additive.
   - Its formula uses only columns of `L`.
   - Every filter can be applied to `L`.

   If any condition fails, write "estimated impact: not computed" with the reason. Otherwise, reuse `l` and `per_row` from step 2 and copy the metric's formula verbatim from the SV:

   ```sql
   SELECT SUM(<metric_expr>)                                                AS raw_total,
          SUM(IFF(p.match_cnt > 1, (<metric_expr>) * (p.match_cnt - 1), 0)) AS estimated_duplicate_contribution,
          SUM(IFF(p.match_cnt = 0, <metric_expr>, 0))                       AS unmatched_value
   FROM l JOIN per_row p ON l.<L_pk> = p.<L_pk>;
   ```

   Label both figures as **estimated**. They show what an equality join at left-row grain would add or leave unmatched. They do not show what the SV actually returns.

4. **Observed impact (SV-confirmed).** Run the metric through the SV twice under the same filters: once with no dimensions, and once grouped by a dimension on `R` with the grouped rows summed. Report `observed_impact = grouped_sum - ungrouped_total` only when both queries succeed.
   - If the SV refuses with a fan trap error, write "observed impact: none; engine refused the query (fan trap guard)" and quote the error.
   - Whether unmatched rows are dropped or grouped under NULL depends on how the SV resolves the join. Report what is returned; do not assume.
   - For non-additive metrics, skip the observed comparison and say why.

5. **Verdict per relationship**:
   - **SKIP**: `left_rows = 0` ("no left rows under the supplied filters"), step 1 prerequisites are not met, or a base table is not readable (quote the error).
   - **FAIL**: `left_rows > 0` and `multi_matched_rows > 0`.
   - **PASS**: `left_rows > 0` and `multi_matched_rows = 0`.
   - **Separate finding, any status:** "Unmatched rows: `<unmatched_rows>` of `<left_rows>`", plus the estimated `unmatched_value` when computed.

### Check 3: Baseline Diff

**Criterion**: Report every difference. The check is **PASS** if there are no breaking changes and **FAIL** if any metric formula changed, any relationship changed, or any field was removed. Additions alone are informational and keep the check at PASS.

1. **Retrieve each definition independently** from its own source: a separate `SYSTEM$READ_YAML_FROM_SEMANTIC_VIEW` call per SV, a supplied file, or pasted text. Pass each retrieved text to the parser unchanged. Never derive one definition from the other, and never retype or reconstruct an export. Record each side's source (query ID, file path, or "pasted") in the evidence.
   - No baseline supplied: mark the check **SKIP** with "no baseline supplied".
   - Either definition cannot be retrieved: mark the check **SKIP** and quote the error.
2. **Parse.** Prefer YAML for both sides. If either definition cannot be parsed reliably, mark the whole check **SKIP** with the specific reason. Never report a partial diff as PASS. Examples of unreliable input:
   - Unbalanced quotes or `$$`
   - Unknown clauses
   - Template syntax such as `{{ }}`
   - Truncated text
   - Duplicate logical names
3. **Normalize** token by token:
   - Keep `"quoted identifiers"`, `'string literals'`, and `$$...$$` bodies byte-for-byte, including case and inner whitespace.
   - Uppercase unquoted identifiers and keywords only.
   - Collapse whitespace and strip `--` and `/* */` comments only outside literals and quoted identifiers.
   - Sort list members (tables, dimensions, metrics, synonyms) by normalized name. Do not reorder tokens inside an expression.
   - Match objects by logical name, scoped by table.
4. Compare:

   | Category | Compare on | Breaking? |
   |---|---|---|
   | Metric formula changed | `expr`, `USING`, `NON ADDITIVE BY`, owning table | Yes |
   | Relationship changed | Left/right tables, join columns, join type (equality/range/ASOF), added or removed | Yes |
   | Field removed | Any dimension, time dimension, fact, metric, or table present in the baseline only | Yes |
   | Primary key changed | `TABLES ... PRIMARY KEY` | Yes (feeds Check 2) |
   | Field added | Any dimension, time dimension, fact, metric, or table present in the current definition only | No |
   | Synonym/comment changed | `synonyms`, `comment`, field `description`, and the top-level SV `description` | No (note it) |

   **Relationship shape:** A relationship with `name`, `left_table`, `right_table`, and `relationship_columns` made only of `left_column`/`right_column` pairs is a standard column-pair relationship. Compare it as an equality join even when `join_type` is absent. If a relationship has any other keys or structure, do not infer equality from a missing `join_type`. Mark the check **SKIP** with "unknown relationship shape: `<name>`".

   **Not compared:** `data_type` and `access_modifier` on dimensions, facts, and metrics. Changes to these keys do not affect the status. List them as "not compared" in the evidence.

5. A logical name that moved tables appears as removed plus added. Flag it as a probable rename and let the user decide.
6. Optional: if Check 1 inputs exist and the baseline is a live SV, run the Check 1 comparison against both versions to show the numeric effect of formula changes.

## Example: Synthetic Retail

All names and values in this example are made up.

**SV `RETAIL_DB.ANALYTICS.SALES_SV`**
- `order_lines` (`FCT_ORDER_LINES`, PK `line_id`): facts `quantity`, `unit_price`, `discount_pct`
- `products` (`DIM_PRODUCT`, declared PK `product_id`)
- `stores` (`DIM_STORE`, PK `store_id`)
- Relationships: `order_lines(product_id) REFERENCES products(product_id)`, `order_lines(store_id) REFERENCES stores(store_id)`
- Metric `order_lines.total_revenue AS SUM(quantity * unit_price * (1 - discount_pct))` (additive)

**User**: "Validate my semantic view SALES_SV: total revenue by month for 2025 should match this SQL, check for join fanout, and compare it to SALES_SV_V1."

```sql
-- reference SQL (user supplied). Functions used: DATE_TRUNC, SUM, YEAR (all approved)
SELECT DATE_TRUNC('month', order_date) AS month,
       SUM(quantity * unit_price)      AS total_revenue
FROM RETAIL_DB.RAW.FCT_ORDER_LINES
WHERE YEAR(order_date) = 2025
GROUP BY 1;
```

**Outcome**
- **Check 1: FAIL.** No duplicate keys on either input. `total_keys 12, n_match 0, n_value_mismatch 12`. Totals are 2,412,300.00 (SV) vs 2,561,900.00 (reference). The SV formula applies `(1 - discount_pct)` but the reference does not.
- **Check 2a: FAIL.** `DIM_PRODUCT` holds SCD2 history without a current-row filter. Counts: `left_rows 1000, unmatched_rows 12, single_matched_rows 958, multi_matched_rows 30, max_matches_per_row 2`. Estimated duplicate contribution is +4,812.50 using the SV formula. Observed impact: the SV query grouped by `products.category` summed to 4,812.50 above the ungrouped total, which confirms the estimate. Fix: declare a unique key or scope the table to current rows. See the `sv_diagnostics` 5b and `range_join` snippets.
- **Finding 2a-u:** 12 of 1,000 lines have no matching product (estimated value 1,140.00).
- **Check 2b: PASS.** Every line matches exactly one store.
- **Check 3: FAIL vs `SALES_SV_V1`.**
  - Formula changed: `total_revenue` went from `SUM(quantity * unit_price)` to `SUM(quantity * unit_price * (1 - discount_pct))`. This also explains Check 1.
  - Relationship changed: `order_lines → stores` moved from `store_id` to `store_key`.
  - Removed field: dimension `products.brand`.
  - Added (info): metric `avg_basket_size`.

## Stopping Points

- After Step 0: confirm the inventory and the scope of the checks.
- Before running user-supplied reference SQL: show its function list and its classification against the approved lists.
- Before loosening the tolerance or skipping a relationship by user choice.

## Common Mistakes

- **Comparing at different grains or filters.** This produces false FAILs. Always build the alignment table first and SKIP if the two sides cannot be aligned.
- **Comparing inputs with duplicate grain keys.** A duplicated key multiplies matches in the join. Probe first and SKIP, naming the input that has duplicates.
- **Plain `=` or an inner join on grain keys.** This drops NULL keys and keys that exist on only one side. Use `EQUAL_NULL` on every grain column, a full outer join, and presence flags.
- **Coalescing NULL to 0.** This hides `NULL_MISMATCH`.
- **Counting from a different query than the evidence.** Take the counts and the sample from the same comparison statement.
- **Summing non-additive metrics.** Omit those totals or compare at the total grain.
- **Reporting an estimate as observed.** The per-row calculation is an estimate. Only an SV query confirms observed impact.
- **Trusting declared PKs.** Snowflake does not enforce them. Check 2 must probe real data.
- **Running SQL that is not fully classified.** If any statement or function is not on the approved lists, skip execution.
- **Reporting a status without SQL or values.** Every row in the report needs evidence or a reason.
- **"Fixing" the SV.** This skill is read-only. Hand off to `semantic-view-patterns` for the fix.
